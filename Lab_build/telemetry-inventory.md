# Telemetry Inventory

This document defines the telemetry mappings used throughout the lab, including the expected event sources, known limitations, and OCSF normalisation targets. Each source is validated locally before forwarding is configured for SIEM01. This separates endpoint collection problems from transport, parsing, and normalisation problems.

### Test 1 — AD authentication to UBU01

**Action**

Authenticate to UBU01 using an Active Directory user account. Perform one successful attempt and one failed attempt locally with `su` and/or remotely with SSH.

**Expected telemetry**

- UBU01: PAM and SSSD authentication records.
- UBU01: `sshd` records when SSH is used.
- DC01: Kerberos authentication activity for the AD-backed account.
- Failed password authentication may generate Kerberos pre-authentication failure telemetry.

**Expected event IDs / records**

- DC01 `4768` — Kerberos ticket-granting ticket (TGT) requested.
- DC01 `4769` — Kerberos service ticket requested, where applicable.
- DC01 `4771` — Kerberos pre-authentication failed.
- UBU01 — PAM, SSSD, and `sshd` success or failure records.

**OCSF target**

- Authentication (`class_uid: 3002`).

**Validation result:** Passed, with a host-configuration warning.

**Gathered telemetry**

- The domain user `b.bradley16@LOCAL.LAB` successfully authenticated to UBU01 using `su`.
- `klist` confirmed a Kerberos TGT for `b.bradley16@LOCAL.LAB` with the service principal `krbtgt/LOCAL.LAB@LOCAL.LAB`.
- Successful and failed authentication activity was generated and the related Kerberos data was checked during validation.
- Evidence: [UBU01 AD session and Kerberos ticket](evidence/telemetry-validation/01-ubu01-ad-kerberos-session.png).

**Discrepancies / fixes**

- The session displayed `cannot change directory to /home/b.bradley16@Local.lab: No such file or directory`. Authentication still succeeded, but the AD user’s Linux home-directory creation or path configuration should be corrected separately.

### Test 3 — Command and process execution on UBU01

**Action**

Run identifiable commands such as `whoami`, `id`, `cat`, and a shell command on UBU01.

**Expected telemetry**

- `auditd` records process execution locally when the `execve` rules are loaded.
- One execution may produce several records sharing the same audit event identifier.
- The combined records identify the executable, arguments, working directory, user, and referenced paths where available.

**Expected event IDs / records**

- `SYSCALL` — syscall result, executable, process IDs, and user IDs.
- `EXECVE` — executed command and arguments.
- `PATH` — executable or referenced file paths.
- `CWD` — current working directory.
- `PROCTITLE` — encoded process command line, when emitted.
- Audit key `process_exec` or `exec`, depending on which rule from `Guide.md` is loaded.

Records must be correlated using the shared audit message identifier, for example `msg=audit(<timestamp>:<serial>)`, before being normalised into one process event.

**OCSF target**

- Process Activity (`class_uid: 1007`, Launch activity).

**Validation result:** Passed.

**Gathered telemetry**

- `whoami`, `nano`, and `cat` were executed on UBU01 and detected by `auditd`.
- The retained `whoami` event contains correlated `PROCTITLE`, `PATH`, `CWD`, `EXECVE`, and `SYSCALL` records under the shared identifier `msg=audit(1787432276.360:34702)`.
- The event records `cwd="/home/wricho5"`, `argc=1`, `a0="whoami"`, `success=yes`, and `exit=0`, together with process and identity fields such as `ppid`, `pid`, `auid`, and `uid`.
- Evidence: [UBU01 auditd records for whoami](evidence/telemetry-validation/02-ubu01-auditd-whoami.png).

**Discrepancies / fixes:** _None. The test confirmed that the shared audit identifier can be used to assemble the record fragments into one OCSF Process Activity event._

### Test 4 — Certificate request from CA01

**Action**

From WinUser01, request a certificate from CA01 using a standard AD user. Test a successful enrolment and, where practical, a denied or unauthorised request.

**Expected telemetry**

- CA01 independently records receipt of the certificate request and its outcome.
- DC01 may record Kerberos TGT and service-ticket activity as the user accesses domain and CA services.
- The CA database may be required to associate the request ID and requester with the issued certificate serial number.

**Expected event IDs / records**

- CA01 `4886` — certificate request received.
- CA01 `4887` — certificate request approved and certificate issued.
- CA01 `4888` — certificate request denied.
- DC01 `4768` — Kerberos TGT requested, where applicable.
- DC01 `4769` — Kerberos service ticket requested, where applicable.

**OCSF target**

- Preferred: a documented `x_` certificate-issuance extension.
- Interim alternative: Entity Management (`class_uid: 3004`) with the semantic limitations documented.

**Validation result:** Passed after CRL remediation.

**Gathered telemetry**

- Initial enrolment attempts reached CA01 and generated events `4886` and `4888` at approximately 13:09–13:10 and 13:26.
- CA01 also logged Certification Authority application warnings, including event IDs `53` and `77`. The denial reported `0x80092013 (CRYPT_E_REVOCATION_OFFLINE)` because the revocation server could not be reached.
- The CRL was refreshed with `certutil -crl`, and Active Directory was updated to use the refreshed CRL.
- A subsequent request succeeded at 13:44:32 and generated events `4886` and `4887`.
- Event `4887` recorded Request ID `4`, requester `LOCAL\\b.bradley16`, and computer `CA-01.Local.lab`.
- The issued certificate was for `Bob`, issued by `Local-CA-01-CA`, and valid from 23 August 2026 to 23 August 2027. Its displayed purposes include remote-computer identity, email protection, and disk encryption.
- Evidence: [CRL failure](evidence/telemetry-validation/04-ca01-crl-offline-error.png), [certificate event sequence](evidence/telemetry-validation/06-ca01-certificate-events.png), [event 4887 details](evidence/telemetry-validation/07-ca01-event-4887-details.png), and [issued certificate](evidence/telemetry-validation/05-issued-certificate-bob.png).

**Discrepancies / fixes**

- The stale CRL caused valid requests to be denied until it was regenerated and republished.
- The retained `4887` view exposes the request ID and requester but does not show a certificate serial number or supplied SAN/UPN. CA-database enrichment remains necessary if those fields are required for issuance-to-authentication correlation.

## CA/PKI normalisation constraint

Certificate request and issuance telemetry does not have a clean stock OCSF class. This is a deliberate project constraint rather than an endpoint collection failure. The selected approach must preserve the requester, subject, template, request ID, certificate serial number, and disposition while documenting any custom extension or semantic compromise.

The validation path is:

1. Confirm the fields emitted by CA01 in events `4886`, `4887`, and `4888`.
2. Determine whether `4887` contains a usable certificate serial number on this Windows build.
3. Enrich the Security events from the CA database if required correlation fields are absent.
4. Compare a documented OCSF `x_` extension with an Entity Management (`3004`) mapping.
5. Validate the selected representation using the project’s OCSF schema-conformance tests.
