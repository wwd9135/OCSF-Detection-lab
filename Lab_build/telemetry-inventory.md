# Telemetry inventory

## Purpose

This document defines the telemetry expected from each validation test, identifies where that telemetry is available in the lab, and records any gaps discovered during testing. Validation is performed locally on each endpoint before logs are forwarded to SIEM01. This separates collection problems from transport, parsing, and normalisation problems.

The inventory covers DC01, CA01, UBU01, and WinUser01. SIEM01 is the downstream destination and is therefore outside the initial endpoint-validation scope.

## Telemetry mapping and validation record

Each test uses the same structure: action, expected telemetry, expected records, OCSF mapping, gathered telemetry, and discrepancies or fixes. “Not yet recorded” means that the source is defined but no test evidence has been added to this inventory.

### Test 1 — AD authentication to UBU01

**Action**

Authenticate to UBU01 using an Active Directory user account. Perform at least one successful attempt and one failed attempt, locally with `su` and/or remotely with SSH.

**Expected telemetry**

- UBU01 records the authentication result through PAM and SSSD.
- UBU01 records the remote session through `sshd` when SSH is used.
- DC01 records Kerberos activity generated by the domain-backed authentication.
- A failed password attempt may produce a Kerberos pre-authentication failure on DC01.

**Expected event IDs / records**

- DC01 `4768` — Kerberos ticket-granting ticket (TGT) requested.
- DC01 `4769` — Kerberos service ticket requested, where applicable.
- DC01 `4771` — Kerberos pre-authentication failed.
- UBU01 — PAM, SSSD, and `sshd` success or failure records.

**OCSF mapping**

- Authentication (`class_uid: 3002`).
- Map the AD username to `user.name`, the result to `status_id`, and Kerberos/SSH to the appropriate authentication protocol fields.

**Gathered telemetry**

_Not yet recorded._

**Telemetry discrepancies / fixes**

_None recorded._

**OCSF mapping**

- Map the target account to `user.name`, the source address to the source endpoint, the logon result to `status_id`, and the Windows logon type to the relevant authentication context.

### Test 3 — Command and process execution on UBU01

**Action**

Run identifiable commands such as `whoami`, `id`, `cat`, and a shell command on UBU01.

**Expected telemetry**

- `auditd` records each process execution locally when the `execve` rules are loaded.
- A single execution may produce several related audit records that share the same audit event identifier.
- The combined records should identify the executable, arguments, working directory, user, and referenced paths where available.

**Expected event IDs / records**

- `SYSCALL` — syscall result, executable, process identifiers, and user identifiers.
- `EXECVE` — command arguments.
- `PATH` — referenced executable or file paths.
- `CWD` — working directory.
- `PROCTITLE` — encoded process command line, when emitted.
- Audit key `process_exec` or `exec`, depending on the final rule loaded from `Guide.md`.

**OCSF mapping**

- Process Activity (`class_uid: 1007`, Launch activity).
- Correlate records by the shared audit event identifier before mapping the executable, arguments, parent process, and user into one normalised event.

**Gathered telemetry**

_Not yet recorded._

**Telemetry discrepancies / fixes**

_None recorded._

### Test 4 — Certificate request from WinUser01

**Action**

From WinUser01, request a certificate from CA01 using a standard AD user. Test a successful enrolment and, where practical, a denied or unauthorised request.

**Expected telemetry**

- CA01 records receipt of the request and whether it was issued or denied.
- DC01 may record Kerberos TGT and service-ticket activity as the user accesses domain and CA services.
- A successful issuance record should preserve the requester and request ID. The certificate serial number may need to be retrieved from the CA database for later issuance-to-authentication correlation.

**Expected event IDs / records**

- CA01 `4886` — Certificate Services received a certificate request.
- CA01 `4887` — Certificate Services approved a request and issued a certificate.
- CA01 `4888` — Certificate Services denied a certificate request.
- DC01 `4768` — Kerberos TGT requested, where applicable.
- DC01 `4769` — Kerberos service ticket requested, where applicable.
- CA database — authoritative request ID, requester, template, disposition, and certificate serial mapping when these fields are not fully exposed in the Security event.

**OCSF mapping**

- Stock OCSF does not provide a clean semantic class for certificate issuance.
- Preferred direction: define and document an `x_` certificate-issuance extension that preserves the requester, template, request ID, subject, serial number, and disposition.
- Interim alternative: map issuance as Entity Management (`class_uid: 3004`) and explicitly document the semantic loss. Issuance must not be represented as authentication merely because the certificate may later be used to authenticate.

**Gathered telemetry**

_Not yet recorded._

**Telemetry discrepancies / fixes**

_Known design gap: events `4886` and `4887` may not expose a supplied SAN/UPN or certificate serial number in a consistently parseable field. If required fields are absent, enrich the event from the CA database and document the join method._

### Test 5 — Active Directory object modification

**Action**

Perform a controlled change on DC01, such as creating a test user, changing an attribute, modifying group membership, moving an object, or deleting the test object. For certificate-template coverage, modify a test `pKICertificateTemplate` object after applying the required SACL.

**Expected telemetry**

- DC01 records the relevant directory service or account-management event.
- Directory Service Changes auditing provides attribute-level evidence only when the audit subcategory and an appropriate object SACL are both configured.
- Sysmon may identify the administrative process used, but it does not report the directory object change itself.

**Expected event IDs / records**

- `5136` — directory service object modified.
- `5137` — directory service object created.
- `5139` — directory service object moved.
- `5141` — directory service object deleted.
- `4720` — user account created, where applicable.
- `4738` — user account changed, where applicable.
- `4726` — user account deleted, where applicable.
- Group-membership event IDs vary by the type and scope of the group being changed.

**OCSF mapping**

- Entity Management (`class_uid: 3004`).
- Preserve the actor, object distinguished name and type, operation, LDAP display name, and old/new values where the source event provides them.

**Gathered telemetry**

_Not yet recorded._

**Telemetry discrepancies / fixes**

_None recorded. If `5136` is absent, verify both Advanced Audit Policy and the target object’s SACL._

### Test 6 — PowerShell and Command Prompt execution on WinUser01

**Action**

Run identifiable commands in PowerShell and Command Prompt on WinUser01. Spawn at least one child process from each shell.

**Expected telemetry**

- Native Windows process auditing records process creation in the Security log.
- Sysmon independently records enhanced process creation details.
- Both sources should identify the process, command line, user, parent process, and process identifiers when configured correctly.

**Expected event IDs / records**

- WinUser01 Security `4688` — a new process was created; command-line content requires the relevant policy setting.
- WinUser01 Sysmon `1` — Process Create.

**OCSF mapping**

- Process Activity (`class_uid: 1007`, Launch activity).
- Map the executable and command line to the process object, the initiating process to the actor process, and the account to the actor user.

**Gathered telemetry**

_Not yet recorded._

**Telemetry discrepancies / fixes**

_None recorded._

## CA/PKI normalisation constraint

Certificate request and issuance telemetry does not have a clean stock OCSF class. This is a deliberate design constraint for the project rather than an endpoint-collection failure. The chosen approach must preserve certificate-specific fields required for detection—particularly requester, subject, template, request ID, serial number, and disposition—while documenting any custom extension or semantic compromise.

The preferred investigation path is:

1. Confirm which fields CA01 emits in events `4886`, `4887`, and `4888`.
2. Determine whether event `4887` contains a usable certificate serial number on this Windows build.
3. Enrich from the CA database if the Security events do not contain the required correlation fields.
4. Compare a documented OCSF `x_` extension with an Entity Management (`3004`) mapping.
5. Validate the selected representation against the project’s OCSF schema-conformance tests.
